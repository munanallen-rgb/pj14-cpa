# PJ14 Auto Backup

## Purpose

Create a local, verifiable recovery backup of the PJ14 cloud deployment while keeping the production stack online. Prefer logical database export and file copies over stopping containers or copying live Postgres data files.

## Quick Start

Run the bundled PowerShell script from the repository root:

```powershell
powershell.exe -ExecutionPolicy Bypass -File .\skills\pj14-autobackup\scripts\backup-pj14-cloud.ps1
```

When running from a restricted Codex sandbox, if the first attempt fails before remote archive output with an SSH error such as `ssh: connect to host 159.65.7.65 port 22: Permission denied`, immediately retry the same script with escalated execution (`sandbox_permissions: "require_escalated"`) so SSH/SCP can use the approved non-sandbox network path. Treat the first failure as an execution-environment issue unless the escalated retry also fails. After the retry, still perform the normal SHA256, `contents.txt`, required-path, and remote-cleanup validation before reporting success.

Defaults:

- SSH target: `root@159.65.7.65`
- Remote root: `/opt/cpa-sub2api`
- Local backup root: `backups/`
- Transfer timeout: `1800` seconds for the `scp` download step.
- Redis data is included by default.

Use parameters when the target changes:

```powershell
powershell.exe -ExecutionPolicy Bypass -File .\skills\pj14-autobackup\scripts\backup-pj14-cloud.ps1 `
  -Server 159.65.7.65 `
  -User root `
  -Port 22 `
  -RemoteRoot /opt/cpa-sub2api `
  -LocalBackupRoot backups `
  -TransferTimeoutSeconds 2100
```

## Backup Contents

Always include the files needed to restore the service:

- `docker-compose.cloud.yml`
- Root `.env`
- CPA1 config/auth/logs: `config.yaml`, `auths/`, `logs/`
- CPA2 config/auth/logs: `instances/cpa2/config.yaml`, `instances/cpa2/auths/`, `instances/cpa2/logs/`
- CPA3 config/auth/logs: `instances/cpa3/config.yaml`, `instances/cpa3/auths/`, `instances/cpa3/logs/`
- Commercial-mode backups if present: `*.bak-commercial`
- Sub2API config/logs/pricing files:
  `sub2api-deploy/.env`,
  `sub2api-deploy/data/config.yaml`,
  `sub2api-deploy/data/model_pricing.json`,
  `sub2api-deploy/data/model_pricing.sha256`,
  `sub2api-deploy/data/logs/`
- Sub2API database logical dump: `dumps/sub2api.dump`, generated with `pg_dump -Fc`
- Redis current files: `sub2api-deploy/redis_data/`, unless explicitly skipped

Do not hot-copy `sub2api-deploy/postgres_data/` from a running server. Use `pg_dump` instead.

## Local Directory Format

Each run creates a timestamped directory:

```text
backups/
  cloud-YYYYMMDD-HHMMSS/
    cpa-cloud-backup-YYYYMMDD-HHMMSS.tar.gz
    cpa-cloud-backup-YYYYMMDD-HHMMSS.tar.gz.sha256
    contents.txt
```

Inside the archive:

```text
./
  backup-manifest.txt
  docker-compose.cloud.yml
  .env
  config.yaml
  config.yaml.bak-commercial
  auths/
  logs/
  instances/
    cpa2/
      config.yaml
      config.yaml.bak-commercial
      auths/
      logs/
    cpa3/
      config.yaml
      config.yaml.bak-commercial
      auths/
      logs/
  sub2api-deploy/
    .env
    data/
      config.yaml
      model_pricing.json
      model_pricing.sha256
      logs/
    redis_data/
  dumps/
    sub2api.dump
```

`contents.txt` is the local manifest generated by `tar -tzf`. Keep it beside the archive for quick inspection without extracting secrets.

## Transfer Behavior and Known Pitfalls

The cloud server can create the archive successfully while the local Windows OpenSSH transfer is slow or returns a misleading status. Do not decide backup success from `scp` exit status alone.

Current script behavior:

- `scp` is allowed to run for `-TransferTimeoutSeconds` seconds, defaulting to 30 minutes.
- If the transfer times out, the script kills the full `scp`/child `ssh` process tree to avoid orphaned Windows OpenSSH sessions.
- If `scp` returns a non-zero exit code after both the archive and `.sha256` files exist locally, the script continues to SHA256 validation.
- A backup is complete only after SHA256 matches, `contents.txt` is generated, required paths are present, and remote temporary files are cleaned or a cleanup warning is reported.

Codex sandbox behavior:

- A pre-archive SSH error like `Permission denied` on port 22 can mean the command ran inside the restricted sandbox instead of the approved SSH/SCP path.
- For this case, retry the same PowerShell backup command with `sandbox_permissions: "require_escalated"` and a short justification for SSH/SCP access.
- If the escalated retry succeeds, report the successful backup and mention that the first failure was sandbox-related.
- If the escalated retry also fails before `ARCHIVE=` output, report the SSH failure and note that no remote archive path was emitted, so remote cleanup status is unknown.

Lessons from the 2026-06-06 incident:

- A local SSH tunnel to the same server was not the root cause; the issue reproduced after the tunnel was closed.
- A 1 MiB `scp` transfer took roughly two minutes in the affected environment, so short command timeouts can falsely classify a valid but slow transfer as failed.
- `sftp`, `scp -O`, and Git for Windows `scp.exe` may show the same slow/hung behavior; switching clients is not guaranteed to fix this on the same machine.
- Do not use unauthenticated public HTTP to transfer the backup archive. The archive contains secrets and must not be exposed on a public interface, even temporarily.
- If transfer diagnostics create remote test files or temporary services, clean them before finishing and verify `/tmp/cpa-cloud-backup-*` is absent.

## Safety Rules

- Do not restart or stop containers during backup.
- Generate temporary files under `/tmp/cpa-cloud-backup-*` only.
- Remove remote temporary archives after local SHA256 validation.
- If SSH cleanup fails, tell the user the exact `/tmp/cpa-cloud-backup-*` path that may remain.
- Treat the local backup as secret material: it contains OAuth tokens, API keys, JWT secrets, and database credentials.

## Validation

After download, verify:

- The SHA256 in `*.sha256` matches the local archive.
- `contents.txt` contains `dumps/sub2api.dump`.
- `contents.txt` contains all three CPA auth directories.
- The remote temporary archive was removed.

If any validation fails, keep the failed local directory for inspection and do not claim the backup is complete.
